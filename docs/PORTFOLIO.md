# 포트폴리오 사례: 모듈별 장비 데이터 수집

2026-10-31: [하이브리드 대시보드](HYBRID_DASHBOARD.md)에 React 화면, C# 원본 검토, ASP.NET Core/SignalR, WebView2 구현과 최신 실패 상태를 정리했습니다. 아래 WPF 구조와 과거 시험은 당시 증거이며 현재 전체 연결 성공을 뜻하지 않습니다.

## 문제와 범위

사용자가 요구사항으로 제시한 문제는 CMP 계열 장비의 수백 개 숫자 태그, 짧게 나타나는 값 이상, CMC·PMC·스케줄러 단위의 수집 경계였습니다. 화면의 최신 값만 남기면 다음 조회 전 끝나는 변화나 오류를 확인하기 어렵습니다.

이 결과는 그 문제를 재현하는 로컬 개발 기반입니다. 독립 에뮬레이터가 데이터를 만들고, 각 모듈 프로세스가 수집·원시 저장·개발용 평가를 맡습니다. 통합 API는 최신 요약을 WPF에 전달합니다. 실장비 통신·현장 보정·고객 데이터·상용 운영은 포함하지 않습니다.

## 구조와 데이터 흐름

~~~mermaid
flowchart LR
  E["CMC / PMC / 스케줄러 에뮬레이터"] --> W["모듈 작업 프로세스<br/>수집 · 품질 검사 · 평가"]
  W --> D[("모듈별 SQLite<br/>원시 배치 · 커서 · 누락 구간")]
  W -->|"커밋 뒤 제한된 최신 요약"| A["통합 API · 프로세스 감독"]
  A --> U["WPF 화면"]
~~~

프로세스는 태그마다 만들지 않고 모듈이나 책임 단위로 둡니다. 한 모듈의 기록 잠금이 다른 모듈의 SQLite writer를 막지 않게 데이터베이스도 모듈별로 나눴습니다. 통합 API에는 원시 태그 전체 대신 최신 관측·품질·진단·경고 요약만 전달합니다. 화면은 기존 유량 프로필 8개 신호를 표시하고, 원시 배치는 모듈 데이터베이스에 남습니다.

## 실제로 구현한 보장

- 기존 8개 신호 스냅샷 계약을 유지하고, 별도 replay 계약은 스냅샷당 1–512개의 숫자 신호와 임의 식별자를 받습니다. 한 페이지는 최대 256개 스냅샷이며 소스 재전송 보존 구간은 최근 4096 순번입니다. 이는 코드 경계이지 검증된 현장 용량은 아닙니다.
- 원시 payload, 수신 시각, 장비·모듈 식별자, deviceId/runId/sequence 커서와 확인된 누락 범위를 SQLite 트랜잭션으로 저장합니다. WAL과 FULL 동기화를 사용합니다. 배치와 커서가 커밋된 뒤에만 새 최신 요약을 공개합니다.
- 동일 ID와 동일 payload 재전송은 중복 저장하지 않습니다. 같은 ID에 내용이 바뀌면 전체 페이지를 거부합니다. 잠금, 디스크 가득 참, commit 실패에서는 원시 행·누락 기록·커서를 함께 되돌립니다. 재시작은 저장된 커서에서 재개합니다.
- 재전송 보존 범위를 넘긴 자료는 누락 구간으로 기록합니다. 무제한 보존이나 무손실을 보장하지 않습니다. 에뮬레이터가 새 run으로 재시작되기 전에 받지 못한 과거 자료는 복구할 수 없습니다.
- GOOD이어도 개발 범위를 벗어난 음수 유량은 원시 증거를 수정하지 않고 평가에서 OUT_OF_RANGE로 표시합니다. 결측·BAD·오래된 입력은 정상 판정 창을 초기화합니다. 품질 문제가 있다고 정상으로 표시하지 않습니다.
- EWMA는 고정 규칙의 ADVISORY입니다. 충분한 유효 입력이 있어야 표시하며, 모델은 학습·장비 보정되지 않았습니다. 평가 창과 경고 상태는 메모리에 있어 프로세스 재시작 뒤 다시 준비됩니다.

구현과 시험의 자세한 조건은 [모듈별 원시 기록 보고서](DURABLE_INGESTION_REPORT.md), [수집기](../src/aegis/collector.py), [저장소](../src/aegis/archive.py), [프로세스 요약 경계](../src/aegis/processes.py), [평가기](../src/aegis/evaluation.py)에서 확인할 수 있습니다.

## 검증과 실패 증거

2026-10-19 보고서에 기록된 과거 로컬 확인은 Python 246개, 독립 에뮬레이터 25개, .NET 74개 시험 통과와 계약 정적 검사입니다. 보고서에는 원격 CI 결과가 없습니다. 개별 재현 코드는 [원시 저장 시험](../tests/test_archive.py)과 [재생 수집 시험](../tests/test_replay_collector.py)에 있습니다. 여기에는 잠금·SQLITE_FULL·commit rollback·재시도·변경된 중복 ID·커서 복구 사례가 포함됩니다.

후속 포트폴리오 검증은 새 가상환경과 한글·공백 경로의 별도 소스 복사본에서 실행했습니다. 설치 스크립트의 JUnit 인수 오류를 발견해 실패를 기록하고 회귀 시험으로 수정했습니다. 최종 Python248개·에뮬레이터25개·.NET74개와 Release 빌드가 통과했습니다. [실행 재현과 기계 판독 증거](REPRODUCIBILITY.md). 같은 호스트와 설치 캐시를 사용했고 원격 CI는 아직 실행하지 않았습니다.

보고서의 서로 다른 시점에 수행한 짧은 시험에서는 100ms 수집의 4모듈 실행이 종료 시 대기 없이 끝났고, 별도 10ms 고속 조건은 데이터가 밀렸습니다. 후속 프로파일에서 중복 사전 변환·JSON 인코딩을 줄였고, 동일 프레임을6회 교차 인코딩한 실험의 직렬화 CPU 시간 중앙값은320.31ms에서78.13ms로 줄었습니다. 전체 프로세스도 A/B/A/B로 같은 설정을 반복했지만 시점별 지연 편차와 잔존 backlog가 있어 전체 처리율 향상이나 지속100Hz 보장은 주장하지 않습니다. 전체 표본·동결한 이전 소스·재실행 명령은 [성능 보고서](PERFORMANCE.md)에 있습니다. FULL 동기화는 계속 유지했습니다.

과거 Windows 로컬 시험에서 소켓·이벤트 루프 시작 실패가 간헐적으로 관측됐고 재실행은 통과했습니다. 원인이 확정되지 않았으며 재발 방지가 증명된 상태도 아닙니다. 상세 기록과 제한 사항은 [보고서의 검증·한계 절](DURABLE_INGESTION_REPORT.md)에 있습니다.

## 결정의 비용과 남은 범위

2026-10-20 사용자 우선순위를 노이즈 속 실제 변화 보존으로 조정했다. 원본과5점 중앙값 추세를 분리하고 매 프레임 미해결 검토 근거를 남기는 경로와 인증 API를 추가했다. 합성39회에서 작은 잡음의 추세 오차는 줄었지만 강한 잡음 속 실제6건 중2건을 놓쳤고, 버스트 잡음만으로265후보/분이 발생했다. 원인 분류 완성으로 표현하지 않는다. [동일 파형/다른 원인 검증·장비 문맥 설계·실패 비용](SIGNAL_REVIEW.md).

모듈별 DB는 writer 충돌 범위를 줄이지만 SQLite WAL 파일과 보관 공간, 백업, 체크포인트, 디스크 용량 관리를 모듈마다 요구합니다. FULL 커밋은 내구성을 우선하며 빠른 수집 조건에서 처리량 비용이 생길 수 있습니다. 별도 프로세스는 CPU 작업과 일부 장애를 분리하지만 총 CPU·메모리·디스크 처리량을 늘려주지는 않습니다.

다음은 구현되지 않았거나 현장 적용 전에 정해야 할 항목입니다.

- 실제 프로토콜, 장비별 태그 사전·단위·범위·보정, 문자열과 스케줄러 이벤트 의미
- 장기 부하·전원 차단 내구성·실장비 기반 처리율 검증
- 보관 기간·압축·디스크 예산 정책, WAL 포함 일관 백업·복구 절차
- 영구 ACK/경고 상태, 임의 태그 검색 화면, 과거 Trend API, Windows 서비스 운영

512개 신호·32개 소스 한도는 입력과 응답의 경계이며 보증 용량이 아닙니다. 10ms 고속 조건의 미달 결과를 숨기지 않고, 처리율과 데이터 나이를 같은 시험 조건에서 확인하는 것이 다음 검증의 기준입니다.

## 제작 과정과 인터뷰에서 설명할 점

이 사례는 AI 지원 구현을 사용했습니다. 요구 범위와 문제 설정은 사용자가 정리한 문서와 아키텍처 지시를 따랐습니다. 모든 코드가 사람 손으로 작성됐다고 주장하지 않습니다. 인터뷰에서는 실제로 설명하고 검토할 수 있는 변경과 결정을 구분해 소개하는 것이 적절합니다.

설명 준비에 쓸 질문:

- 원시 기록을 통합 DB 하나가 아니라 모듈별 SQLite로 분리한 이유와 그 비용은 무엇인가?
- 같은 배치가 다시 왔을 때 저장된 커서와 원시 행은 어떻게 일관성을 지키는가? 같은 순번에 값이 달라지면 어떻게 되는가?
- API 응답 지연과 관측 데이터 나이를 왜 각각 봐야 하는가?
- 저장 잠금이나 디스크 가득 참에서 화면에 최신 값을 내보내지 않는 이유는 무엇인가?
- 10ms 목표가 실패했을 때 다음으로 분리해 측정할 병목은 무엇이며, 시험 조건은 어떻게 통제할 것인가?
- 실제 장비에 연결하기 전에 어떤 태그 매핑·보정·장기 복구 검증이 필요한가?
