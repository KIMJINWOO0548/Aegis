## 어떻게 구분할 것인가

단일 파형의 진폭·길이만으로 센서 잡음과 공정 변화를 확정하지 않는다. 같은 측정값을 만드는 두 원인은 관측값만으로 구분할 수 없다. 추가 근거가 필요하다.

| 근거 | 확인할 질문 | 현재 범위 |
|---|---|---|
| 운전 상태·레시피·설정값 | 명령에 따라 예상한 변화인가? 전환 중인가? | mode/state와 설정값 앵커 변화를 만나면 문맥을 다시 준비 |
| 관련 센서 | 압력·전류·밸브 반응이 함께 나타나는가? | 같은 시각의 변화 목록 기록, 원인 확정 안 함 |
| 센서 지연과 물리적 관계 | 압력→유량처럼 설명 가능한 순서·지연인가? | 미구현, 장비별 관계·센서 지연 보정 필요 |
| 지속·반복·주파수 | 레시피 단계에 맞는 반복인가? 계측기 고유의 잡음인가? | 원시 시각·표본 간격·피크 기록, 주파수/반복 분류 미구현 |
| 독립된 결과 | 다른 계측·공정 결과·정비 확인과 맞는가? | 실제 라벨·참조 센서 없음, 현장 검증 필요 |

관련 센서의 동시 변화도 공통 전기 노이즈일 수 있다. 반대로 한 센서만 변했다고 가짜라고 할 수도 없다. 이런 경우 `UNRESOLVED`로 남긴다. `GOOD`은 입력 품질이며 실제 공정의 정상·비정상 정답이 아니다.

## 이번 코드의 두 경로

`actualFlow − setpointFlow`의 signed residual을 사용한다. 수집된 원본과 원래 quality는 바꾸지 않는다.

1. 최근 5개 유효 점의 인과적 중앙값을 `trendErrorLpm`으로 제공한다. 미래 데이터를 보지 않는 파생 추세다. 짧은 실제 변화도 약해지거나 지연될 수 있으므로 원본을 대체하지 않는다.
2. 현재 점을 넣기 전 최근 1초/최대256개 점의 중앙값·MAD와 원시 오차를 비교한다. 5점·200ms의 문맥이 준비된 상태에서 `max(0.5 L/min, 6×MAD)`를 넘으면 즉시 검토 이벤트를 연다. 이 수치는 합성 개발 가정이다. 6×MAD를 6σ나 발생 확률로 해석하지 않는다.

MAD는 국소 산포를 설명하기 위해 사용한다. [NIST의 정의](https://www.itl.nist.gov/div898/software/dataplot/refman2/auxillar/mad.htm)를 참고했다. 중앙값과 MAD로 이상점을 찾고 값을 교체하는 [Hampel 필터](https://www.mathworks.com/help/signal/ref/hampel.html)와 달리, 이 구현은 인과적 과거 문맥으로 검토 후보를 만들며 원시 점을 교체하지 않는다. 현장 적합성은 이 자료만으로 보장되지 않는다.

이벤트가 열린 동안 기준과 임계값을 고정하고 해당 점을 다음 이벤트 기준에 넣지 않는다. 지속 변화를 새 정상으로 학습하거나 정상 복귀를 새 이상으로 오인하지 않기 위해서다. 원래 문맥 범위로 돌아왔다는 사실은 이벤트 종료 사유일 뿐 공정 고장 복구라는 판단이 아니다.

이벤트에는 원본 observationId, 시작·마지막 관측·닫힌 시각, 원시 오차 최소·최대, 기준 대비 최대 편차, 표본 수·표본 간 최대 간격, 관련 센서를 남긴다. 100ms 변화라도 몇 점이 관측됐는지 함께 봐야 한다. 표본 사이에 일어난 더 짧은 변화나 실제 지속시간은 복원했다고 주장하지 않는다.

결측·BAD·범위 오류·순번 누락·1.5초 초과 시간 공백·mode/state 변경·설정값 앵커 대비0.5 L/min 변화 시 문맥을 초기화한다. 진행 중 기록은 그 사유로 닫고 복구로 표시하지 않는다. 문맥 부족은 `WARMING`, 근거가 남으면 `REVIEW_REQUIRED`, 연결 불가는 `UNAVAILABLE`이다. `TRACKING`은 검토 후보가 아직 없다는 뜻이며 설비 정상 판정이 아니다.

## 조회와 재현

모듈 프로세스가 원본을 커밋한 후 분석한다. 엄격한 `FlowReview`/`FlowExcursion` 모델로 제한된 요약만 통합 프로세스에 전달한다. 기존 EWMA diagnostics와 WPF 계약은 유지하며, 다음 별도 인증 API에서 확인한다.

```powershell
$headers = @{ 'X-Aegis-Token' = $env:AEGIS_API_TOKEN }
Invoke-RestMethod -Uri 'http://127.0.0.1:8765/v1/devices/EQ-SUPPLY-01/signal-review' -Headers $headers
```

기존 API를 위 포트와 토큰으로 실행한 경우의 예시다. `run_emulator_demo.py`는 임의 포트·자식 전용 토큰을 만들기 때문에 이 예시를 그대로 붙이지 않는다. API 실행 옵션과 소스 구성은 기존 수집 안내를 따른다.

```powershell
.venv\Scripts\python.exe -m pytest tests/test_signal_review.py tests/test_signal_review_integration.py
.venv\Scripts\python.exe scripts/validate_signal_review.py
.venv\Scripts\python.exe scripts/run_emulator_demo.py --headless --isolate --count 1 --scenario NOISY-FLOW --interval-ms 50 --seconds 15
```

`NOISY-FLOW`는 유효한 작은 잡음과 4초마다100ms의 유량 하강·압력 변화를 보낸다. scenario·정답·잡음 성분은 wire에 넣지 않는다. 기존 `TRANSIENT`의 −5는 범위 오류 검증이므로 실제 유효 공정 변화 검증과 구분한다. 새 검토 기록의 WPF 표시는 이번 범위에 포함하지 않는다.

최근32개 이벤트만 메모리에 있고 버려진 요약 수는 `omittedEventCount`로 보인다. 재시작 시 파생 상태는 초기화된다. 원본은 SQLite에 남는다. 별도의 영구 검토/ACK 저장은 아직 없다. 느린 drift는 국소 변화 후보에 잡히지 않을 수 있으므로 setpoint-relative 장기 EWMA를 함께 유지한다.

## 성공 기준과 다음 단계

같은 파형에 서로 다른 원인을 붙인 합성 쌍은 입력 해시와 검토 결과가 같아야 하고, 둘 다 `UNRESOLVED`여야 한다. 검증기만 clean truth·잡음 성분·원인 라벨을 알며 분석기는 공개 관측값만 받는다.

노이즈만 있는 구간의 추세 RMSE, 실제 변화의 새 후보 발생 회수·발생 지연, 원시 피크 보존, 이벤트 밖 후보 수/분을 별도로 확인한다. 추세 RMSE 감소가 실제 공정 변화 판별 정확도를 의미하지 않는다. 실제100ms pulse가 평활 추세에서 약해지는 사례도 실패 비용에 포함한다. 강한 잡음으로 가려진 실제 변화의 누락도 공개한다.

검증 표본과 관측 결과는 [원시 기계 판독 결과](evidence/signal-review.json)에 있다. 지속·단계 전환·센서 지연·공통 잡음의 분포가 합성과 다를 수 있으므로 현장 정답률로 일반화하지 않는다. 다음 단계는 장비별 신호 관계와 지연을 명시하고, 레시피 전환을 포함한 라벨 자료를 분리해 검증하는 것이다. 원인을 설명할 추가 관측이 없는 경우 판단 보류를 유지한다.
